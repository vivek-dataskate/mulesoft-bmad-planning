# MuleSoft BMAD Planning System

> **Tech lead use only.** This repo contains BMAD agents, standards, and scaffold tooling.
> Developers never see this repo — they receive a generated GitHub repo they open directly in Codespace.

---

## Background & Design

### Why this exists

MuleSoft projects have a recurring problem: every new engagement starts from scratch. A tech lead
spends the first week making the same decisions — which integration pattern, which connectors,
how to handle errors, how to structure flows — before a developer writes a single line of code.
The decisions are often inconsistent between projects, and junior developers on new engagements
have no guardrails.

This system solves that by encoding the decisions once, at the right level of abstraction, and
automating everything downstream.

### How it was designed

The standards in this repo are grounded in three bodies of work:

1. **Enterprise Integration Patterns** (Hohpe & Woolf, 2003) — the canonical catalog of 65
   messaging patterns. Every integration scenario in this repo maps back to one or more of these
   patterns. Where the original book is silent (flow control, backpressure, TTL), Hohpe's more
   recent writing fills the gap.

2. **MuleSoft API-Led Connectivity** — the 3-layer architecture (system / process / experience)
   that MuleSoft recommends for all integrations. Every generated project enforces this layering
   through naming conventions, flow structure, and connector placement.

3. **Practical judgment** — the EIP catalog is from 2003. Some patterns are obsolete; some
   MuleSoft-specific patterns have no EIP equivalent. The standards apply first-principles thinking
   (coupling, flow control, compensation strategy) and make a call on what to use in practice
   given current MuleSoft tooling.

The research behind the standards lives in `docs/PATTERNS_RESEARCH.md` — a living reference
the Architect consults and extends over time. It explains the *why* behind standards decisions
but does not drive them directly; `standards/MULESOFT_DESIGN_STANDARDS.md` is the constitution.

### What you get out

For any new client engagement:

- **A PRD** — structured requirements extracted from raw discovery docs by the Analyst agent
- **An architecture doc + decisions.json** — integration pattern selected, connectors identified,
  NFRs documented, error handling decided, by the Architect agent
- **Sprint stories** — MuleSoft-specific, referencing exact file names and acceptance criteria,
  generated by the PM agent
- **A compiling Mule project** — valid XML, correct pom.xml, global error handler, MUnit stubs,
  CI/CD config — generated by the scaffold tool and pushed to a new GitHub repo
- **A Codespace URL** — the developer clicks it, the project opens, it compiles, they fill in TODOs

From discovery docs to a developer writing code: under an hour, with consistent standards every time.

## What This Repo Does

Takes any client discovery document and produces a ready-to-open MuleSoft project:

```
Discovery docs  →  BMAD Analyst  →  BMAD Architect  →  BMAD PM  →  Scaffold Generator  →  Client dev repo
```

The developer opens the generated GitHub repo in a Codespace, gets a compiling Mule project with structured TODO comments, and starts delivering — no blank files, no guessing structure.

## Quick Start — New Client

### 1. Drop discovery docs into intake folder
```
projects/{client}/intake/
```
Accepted: transcripts, requirements docs, slide decks, email threads, architecture diagrams.

### 2. Run BMAD Analyst
Open Claude Code and say:
```
Talk to Mary (the analyst). Analyse all docs in projects/{client}/intake/ and produce projects/{client}/prd.md
```

### 3. Run BMAD Architect
```
Talk to Winston (the architect). Read projects/{client}/prd.md and standards/MULESOFT_DESIGN_STANDARDS.md.
Walk the 6-level decision tree. Produce projects/{client}/architecture.md and projects/{client}/decisions.json
```

Verify `decisions.json` is valid against `standards/decisions-schema.json` before proceeding.

### 4. Run BMAD PM
```
Talk to John (the PM). Read projects/{client}/decisions.json and story-library/.
Generate projects/{client}/stories.md
```

### 5. Generate and push client repo
```bash
node scaffold/generate.js --decisions projects/{client}/decisions.json --output /tmp/{client}-mule
bash scaffold/create-client-repo.sh --client {client} --org {your-github-org}
```

The script creates `github.com/{org}/{client}-mule`, pushes code, and prints the Codespace URL.

| Folder | Purpose |
|--------|---------|
| `standards/` | MULESOFT_DESIGN_STANDARDS.md, decisions schema, connector registry |
| `standards/scenarios/` | One reference file per integration pattern |
| `templates/` | PRD, architecture, story templates |
| `templates/connectors/` | XML config stubs per connector |
| `story-library/` | Reusable story templates the PM agent references |
| `scaffold/` | generate.js scaffold generator + XML templates |
| `scaffold/xml-templates/` | Source XML files the generator renders |
| `projects/{client}/` | One folder per client engagement |

## Standards Reference

### Runtime
- **Mule 4.8.0 / Java 17** — all new projects
- **CloudHub 2.0** — default deployment (not CloudHub 1.0)
- **Runtime Fabric** — regulated and government tiers

### API-Led Connectivity (mandatory)
Every integration uses 3-layer architecture:
- `{system}-sys-api` — wraps ONE backend system
- `{domain}-proc-api` — orchestrates, business logic
- `{consumer}-exp-api` — formats for specific consumer

### Security Tiers
| Tier | Controls |
|------|---------|
| `internal` | client-id-enforcement + rate-limiting |
| `partner` | oauth2-client-credentials + rate-limiting |
| `regulated` | oauth2 + JWT via Flex Gateway + Secrets Manager |
| `government` | mTLS + oauth2 + JWT + Secrets Manager + field-encryption |

### Error Handling (mandatory)
- Global error handler in `error-handler.xml`
- Standard error envelope: `{correlationId, errorCode, message, timestamp, failingComponent}`
- DLQ routing for all async flows
- Never expose Java stack traces

## MuleSoft MCP Server

Install once per machine:
```bash
npm install -g mulesoft-mcp-server
```

Available tools: `create_mule_project`, `implement_api_spec`, `generate_mule_flow`,
`generate_munit_test`, `search_asset`, `deploy_mule_application`, `create_api_spec_project`

Use `search_asset` when the architect encounters a system not in `connector-registry.json`.

## Adding a New Connector to the Registry

Edit `standards/connector-registry.json` and add:
```json
"{connector-key}": {
  "groupId": "...",
  "artifactId": "...",
  "version": "...",
  "auth": "...",
  "configTemplate": "templates/connectors/{connector}-config.xml",
  "exchangeUrl": "https://anypoint.mulesoft.com/exchange/...",
  "propertiesRequired": ["key1", "key2"]
}
```
Then create the corresponding XML stub in `templates/connectors/`.
