# MuleSoft BMAD Planning — Test Strategy

> Last updated: May 2026
> Owner: Vivek Yadlapalli (vivek@dataskate.ai)

---

## Overview

This system has two distinct test layers. Both must pass before any change is merged.

```
Layer 1 — Planning Repo (Node.js / Jest)
  What:   Tests the scaffold generator, template engine, and pipeline scripts
  Where:  tests/unit/  and  tests/integration/
  Runner: Jest (npm test)
  Gate:   CI blocks merge if any test fails or coverage < 80%

Layer 2 — Generated Client Projects (MUnit / Maven)
  What:   Tests the Mule XML flows generated by the scaffold
  Where:  src/test/munit/ in each generated {client}-mule/ repo
  Runner: MUnit (mvn munit:test)
  Gate:   Deploy blocked if coverage < floor (per pattern, see §4)
```

---

## §0 — Test Pyramid

```
                  ┌────────────────────────────┐
                  │   E2E / Business Flow       │  ← Full flow from trigger to target
                  │   (MUnit + external stubs)  │    Verifies complete business scenarios
                  ├────────────────────────────┤
                  │   Integration               │  ← Scaffold output validation (Node.js)
                  │   (Jest)                    │    MUnit: cross-flow, error chain, retry
                  ├────────────────────────────┤
                  │   Component                 │  ← Single flow in isolation
                  │   (MUnit per flow file)     │    Mock all connectors; test transform logic
                  ├────────────────────────────┤
                  │   Unit                      │  ← Individual functions (Node.js)
                  └────────────────────────────┘    Profile, coverage floor, template engine
```

Every PR must pass ALL layers before merge. The CI gate runs:

```
1. npm test           — Layer 1: Unit + Integration (scaffold generator)
2. mvn munit:test     — Layer 2: Component + E2E (Mule flows) in client repo
```

### 2.2 Mandatory Test Cases (All Patterns)

Every generated MUnit file must contain these three test cases at minimum:

#### TC-1: Happy Path

```
Given:  Valid payload with all required fields
When:   Flow executes with all connector mocks returning success
Then:
  - Response HTTP status = expected (200/201/202 per flow type)
  - correlationId present and unchanged in response
  - Downstream connector called exactly 1 time
  - Response body matches expected schema (field-level assertions, not just HTTP 200)
  - No exception propagated
```

#### TC-2: Connectivity Failure → Error Envelope

```
Given:  Valid payload
When:   Target connector mock throws HTTP:CONNECTIVITY (or MULE:CONNECTIVITY / DB:CONNECTIVITY)
Then:
  - Global_Error_Handler catches via on-error-continue
  - vars.httpStatus = 503
  - payload.errorCode = 'SERVICE_UNAVAILABLE'
  - payload.correlationId present
  - payload.timestamp present
  - No Java stack trace in payload
  - Primary flow does NOT propagate the error (on-error-continue)
```

#### TC-3: Validation Failure → Invalid Message Channel

```
Given:  Payload with missing required field (e.g. empty body or null id)
When:   Flow executes (no connector mocks needed — validate before connector calls)
Then:
  - vars.httpStatus = 400
  - payload.errorCode = 'VALIDATION_ERROR'
  - Route goes to invalid-messages-queue (NOT DLQ)
  - Downstream connector called 0 times
  - Primary flow continues if other flows still running
```

### 2.3 Pattern-Specific Additional Test Cases

#### Async Consumer Patterns (B, F, M)

| TC | Name | Description |
|----|------|-------------|
| TC-4 | Duplicate message — idempotency | Second delivery of same messageId → ACK + skip, downstream connector called 0 times |
| TC-5 | DLQ routing after max retries | Valid payload, connector throws CONNECTIVITY on every attempt → after maxRetries exhausted, message published to DLQ, MANUAL ack NOT called on primary |
| TC-6 | MQ ACK only after successful processing | Mock connector returns success → `anypoint-mq:ack` called once, `anypoint-mq:nack` never called |

#### Scheduled Sync (D)

| TC | Name | Description |
|----|------|-------------|
| TC-4 | Watermark advances after successful run | Object Store value updated to last processed timestamp after successful batch |
| TC-5 | Watermark NOT advanced on partial failure | If downstream connector throws mid-run → watermark NOT updated (old value preserved) |
| TC-6 | Empty result set — no downstream call | Scheduler fires, source returns 0 records → downstream not called, no error |

#### Batch (C)

| TC | Name | Description |
|----|------|-------------|
| TC-4 | Failed records reported, batch completes | 1 of N records fails in On Complete phase → batch finishes, failed count reported in summary |
| TC-5 | Batch step processes each record independently | 3 records in input → connector called 3 times with correct payloads |
| TC-6 | Large batch respects maxConcurrency | Batch thread count ≤ maxConcurrency from decisions.json |

#### API Aggregation (I)

| TC | Name | Description |
|----|------|-------------|
| TC-4 | Partial failure — one leg fails | One scatter-gather leg mock throws CONNECTIVITY → aggregate response includes error for that leg, other legs succeed |
| TC-5 | All legs succeed | All N leg mocks return success → merged response contains all N results |
| TC-6 | Timeout on one leg | One leg mock throws HTTP:TIMEOUT → that leg error appears in aggregate, response still returned |

#### Process Orchestration (H)

| TC | Name | Description |
|----|------|-------------|
| TC-4 | Mid-saga failure → compensating transaction | Step 2 fails → compensating flows for Step 1 fire in correct order |
| TC-5 | Status polling returns COMPLETED | Object Store contains COMPLETED state → status endpoint returns 200 + result |
| TC-6 | Status polling returns IN_PROGRESS | Object Store contains IN_PROGRESS → status endpoint returns 202 + status |

#### Auth Token Expiry (OAuth2 Flows — any pattern)

| TC | Name | Description |
|----|------|-------------|
| TC-auth | Token refresh on 401 | Connector mock throws HTTP:UNAUTHORIZED first call → one refresh attempt → retry succeeds |

#### Notification Flows (N, or secondary notification)

| TC | Name | Description |
|----|------|-------------|
| TC-notif | Notification failure does not break primary flow | Slack/email mock throws exception → primary flow continues, WARN logged, no exception propagated |

#### AI Integration (`aiIntegration.enabled = true`)

| TC | Name | Description |
|----|------|-------------|
| TC-ai | AI timeout → fallback | AI connector mock throws timeout → fallback value used → primary flow continues |

### 2.4 NFR Test Cases (Non-Functional)

These verify cross-cutting behaviour. One test per cross-cutting concern per flow.

| NFR | Test Name | Assertion |
|-----|-----------|-----------|
| **Correlation ID propagated** | `{flow}-correlation-id-propagation-test` | correlationId in request equals correlationId in response and in any downstream mock call args |
| **No PII in logs** | Manual review gate in Dev Agent VR | Log lines captured by MUnit do not contain email, SSN, card number patterns |
| **Error envelope schema** | Covered by TC-2 per flow | `{correlationId, errorCode, message, timestamp, failingComponent}` all present |
| **Response time SLA** | `{flow}-latency-test` | MUnit timer assertion: flow completes within `decisions.json nfr.latency` value |
| **Idempotency key TTL matches messageTtl** | `{flow}-dedup-ttl-test` | Object Store TTL ≥ `flowControl.deduplicationTtlMinutes` |
| **DLQ queue name matches decisions.json** | `{flow}-dlq-routing-test` | `anypoint-mq:publish` destination = `errorHandling.dlqName` value |
| **Invalid Message Channel ≠ DLQ** | Covered by TC-3 per flow | Validation failures route to `invalidMessageChannelName`, not `dlqName` |

## §4 — Coverage Floors by Pattern

| Pattern | Floor | Rationale |
|---------|-------|-----------|
| request-reply (A) | **80%** | Sync API — every code path exercised |
| api-aggregation (I) | **80%** | Multiple legs need individual coverage |
| event-driven (B) | **75%** | Async — connector calls excluded |
| pubsub-fanout (M) | **75%** | Same as B |
| batch (C) | **75%** | Batch scope lines are harder to instrument |
| data-migration (K) | **75%** | One-time bulk — scaffold stubs are minimal |
| outbound-notification (N) | **60%** | Fire-and-forget; notification failure is write-off |
| all others | **80%** | Default conservative floor |

Coverage measurement **excludes** connector call operations (they are mocked; measuring them is meaningless and misleading).

## §5 — Connection / Integration Error Test Taxonomy

All connectivity error scenarios follow the same test pattern. Use this taxonomy to name tests consistently:

```
{flow-name}-{system}-{error-type}-test

Examples:
  get-account-salesforce-connectivity-test
  sync-orders-netsuite-timeout-test
  publish-event-mq-connectivity-test
  fetch-records-db-connectivity-test
```

| Error Category | MUnit Error Type | Expected Behaviour |
|---------------|-----------------|-------------------|
| **HTTP downstream unavailable** | `HTTP:CONNECTIVITY` | 503 + retry (sync) or DLQ (async) |
| **HTTP timeout** | `HTTP:TIMEOUT` | 503 + retry |
| **HTTP auth failure** | `HTTP:UNAUTHORIZED` | 401 + one refresh attempt + halt |
| **HTTP forbidden** | `HTTP:FORBIDDEN` | 403 + halt, no retry |
| **MQ unavailable** | `ANYPOINT-MQ:CONNECTIVITY` | retry → DLQ |
| **DB unavailable** | `DB:CONNECTIVITY` | 503 + retry → DLQ (async) or 503 (sync) |
| **SFTP unavailable** | `SFTP:CONNECTIVITY` | 503 + log + alert |
| **Validation failure** | `VALIDATION:NULL` / `VALIDATION:INVALID_VALUE` | 400 → invalid-messages-queue (no retry) |
| **OAuth token expired** | `HTTP:UNAUTHORIZED` | one refresh attempt → retry |
| **Unhandled exception** | `MULE:UNKNOWN` | 500 → DLQ + log ERROR |

## §6 — FR and NFR Verification in Dev Agent

The Dev Agent (`bmad-agent-dev`) runs in the client repo and verifies all stories from `stories.md`. For each story it checks:

### FR Verification Checklist

```
□ Each story's Acceptance Criteria checkbox addressed in code or test
□ Every FR has at least one corresponding MUnit test case
□ All connector operations mocked (no live calls in test suite)
□ Test suite passes with mvn munit:test
□ Coverage floor met per pattern (from decisions.json primaryPattern)
```

### NFR Verification Checklist

```
□ volume:        Load test result (or capacity estimate) matches decisions.json nfr.volume
□ latency:       Latency assertion in MUnit matches decisions.json nfr.latency
□ availability:  Global error handler present; DLQ configured; retry policy matches decisions.json
□ throughput:    maxConcurrency set in MQ subscriber ≤ decisions.json flowControl.maxConcurrency
□ idempotency:   Object Store deduplication TTL ≥ decisions.json flowControl.deduplicationTtlMinutes
□ correlation:   correlationId flows end-to-end (assertion in TC-NFR-correlation)
□ no-hardcoded:  No credentials, URLs, or env-specific values inline in XML (grep check)
□ logging:       No PII patterns in log lines (regex grep on logger messages)
□ error-envelope: All error paths produce {correlationId, errorCode, message, timestamp, failingComponent}
```

## §9 — Test Authoring Rules

1. **Mock ALL connector operations** — zero live calls to external systems during any test
2. **Assert on specific field values** — not just HTTP status codes
3. **Do NOT mock DataWeave transforms** — test the transform logic, only mock connectors
4. **Use `munit-tools:assert-that`** — not the deprecated `munit:assert-payload-equals`
5. **Mock config-ref must match exactly** — `attributeName="config-ref" whereValue="..."` must match the actual config-ref in the flow under test
6. **TC-3 validation test** is generated with `ignore="true"` — developer enables it after adding validation to the flow
7. **Coverage excludes connector operations** — do not add connector-call lines to increase coverage numbers; add real business-logic assertions instead
8. **DLQ routing tests** must assert the `anypoint-mq:publish` destination equals `decisions.json errorHandling.dlqName`
9. **Correlation ID tests** must assert the correlationId is the same value at entry and exit of the flow
10. **Notification tests** must assert the primary flow completes even when the notification connector throws

## §10 — E2E Business Flow Tests

End-to-end tests verify the complete business scenario from trigger to final target system write.  
They run **within MUnit** using a full set of system mocks so no live calls leave the container.

### 10.1 What Counts as an E2E Test

An E2E test exercises the complete trigger→process→target chain:

```
[Trigger]
  HTTP POST / MQ message / Scheduler fire / SFTP file drop
    ↓
[Experience API]   (validates, enriches, formats for consumer)
    ↓
[Process API]      (orchestrates, applies business rules, handles errors)
    ↓
[System API(s)]    (calls downstream connector, formats for system)
    ↓
[Target System]    (mocked — asserts on call payload + call count)
```

### 10.2 E2E Test Case Template

Name pattern: `{domain}-e2e-{scenario}-test`

```xml
<!-- Example: create-account-e2e-success-test -->
<munit:test name="{domain}-e2e-{scenario}-test"
            doc:name="E2E: {Scenario description}">

  <munit:behavior>
    <!-- Mock ALL external systems at the boundary (no live calls) -->
    <!-- Source system mock (if pulling data) -->
    <!-- Target system mock — capture call args for assertion -->
  </munit:behavior>

  <munit:execution>
    <!-- Trigger the entry-point flow with a realistic business payload -->
    <munit:run-flow name="{experience-layer-flow}">
      <munit:event>
        <!-- Full realistic payload — not just {id: "test"} -->
      </munit:event>
    </munit:run-flow>
  </munit:execution>

  <munit:validation>
    <!-- Business outcome assertions — not just HTTP 200 -->
    <!-- 1. Target system called with correct payload -->
    <!-- 2. correlationId propagated end-to-end -->
    <!-- 3. Response matches expected business schema -->
    <!-- 4. No errors generated (DLQ publish count = 0) -->
  </munit:validation>
</munit:test>
```

### 10.3 Required E2E Scenarios Per Flow Group

| Scenario | Trigger | Business Outcome to Assert |
|----------|---------|---------------------------|
| **Golden path** | Valid complete payload | Target system receives transformed payload; response = expected |
| **Missing optional field** | Payload without optional fields | Flow completes; target called with defaults applied |
| **Downstream returns partial data** | Source mock returns partial record | Transform handles nulls; target receives enriched record |
| **Rate limit hit on target** | Target mock returns HTTP 429 | Retry fires; after backoff, target called again; success on retry |
| **Target creates duplicate (idempotency)** | Second identical request | Idempotency check fires; target NOT called on duplicate |
| **Multi-system flow — one system slow** | One mock delays 2s | Flow completes within latency SLA; other systems not affected |

### 10.4 E2E Business Scenarios by Integration Type

#### Salesforce → NetSuite (Opportunity-to-Order)

```
E2E-1: Salesforce Closed-Won opportunity → NetSuite Sales Order created
  Given:  SF opportunity mock returns CLOSED_WON with full line items
  When:   Event-driven flow fires
  Then:   NetSuite order mock called once with correct customer ID, lines, currency
          correlationId matches across SF mock call args + NS mock call args
          Response: 201 Created from NS mock

E2E-2: Opportunity with missing billing address
  Given:  SF opportunity mock returns record without BillingCity
  When:   Flow fires
  Then:   Validation routes to invalid-messages-queue (not DLQ)
```

## §11 — Component Tests

Component tests isolate a single flow file and verify all its execution paths in detail.  
More granular than E2E — tests one logical unit, not the full chain.

### 11.1 What a Component Test Covers

```
One flow file = one set of component tests

Tests in scope:
  ✓ Happy path — nominal input + all mocks returning success
  ✓ Each error path in the flow (one test per error-handler branch)
  ✓ Each DataWeave transform (transform called with correct input; output shape asserted)
  ✓ Each conditional branch (if/choice router — one test per branch)
  ✓ Boundary values (empty list, single record, max-size record)

NOT in scope (covered by E2E or unit):
  ✗ Cross-flow orchestration (belongs in E2E)
  ✗ DataWeave function internals (belongs in DWL unit test)
```

### 11.2 Required Component Tests per Flow File

| Component | Mandatory Tests |
|-----------|----------------|
| **HTTP Listener flow** | Happy path, 400 (validation), 401 (no creds), 503 (downstream down), correlationId present |
| **MQ Subscriber flow** | Happy path, duplicate (idempotency), connectivity fail → DLQ, MANUAL ack timing |
| **Scheduler flow** | Happy path, empty source result, watermark update, source connectivity fail |
| **SFTP listener flow** | Happy path, file parse error, SFTP connectivity fail, empty file |
| **Process/Orchestration flow** | Happy path, step-2 failure → compensating tx, status poll states |
| **DataWeave transform** | Required fields present, optional fields null-safe, enum mapping, date format |
| **Error handler** | Each error type routes to correct handler (9 error types — see §3 matrix) |

### 11.3 DataWeave Component Tests

DataWeave files in `src/main/resources/dwl/` must have corresponding component tests.  
Since DWL runs inside Mule, test them through the flow, not in isolation.

| Test Pattern | Description |
|-------------|-------------|
| `{transform}-nominal-test` | All fields present → output matches schema exactly |
| `{transform}-null-optional-test` | Optional fields null → output omits field or uses default |
| `{transform}-max-length-test` | String fields at max allowed length → no truncation error |
| `{transform}-date-format-test` | Input date in source format → output in target format (ISO-8601) |
| `{transform}-enum-mapping-test` | All known enum values → correct target enum output |

## §12 — Retry Tests

### 12.1 Retry Behaviour Assertions

Every flow that has `errorHandling.strategy = retry-then-dlq` needs these tests:

| Test | Scenario | Assert |
|------|----------|--------|
| **First attempt succeeds** | Mock returns success on call 1 | Connector called exactly 1 time |
| **Retry succeeds on attempt 2** | Mock throws on call 1, returns success on call 2 | Connector called 2 times; final result = success |
| **Max retries exhausted → DLQ** | Mock always throws | Connector called `maxRetries + 1` times; DLQ `anypoint-mq:publish` called 1 time |
| **DLQ message payload correct** | After DLQ publish | DLQ payload contains `{correlationId, errorCode, failingFlow, timestamp, originalPayload}` |
| **MANUAL ack withheld until success** | Async MQ consumer | `anypoint-mq:ack` called 0 times during retry; called 1 time after final success |
| **NACK on max retry** | Async MQ consumer after DLQ | `anypoint-mq:nack` called after DLQ publish (or MANUAL ack called, not nack — per pattern) |
| **Backoff intervals respected** | Exponential backoff | Assert mock call timestamps spaced ≥ 30s, ≥ 90s, ≥ 270s |

### 12.2 Retry Table Verification

From `PLANNING_CONTEXT.md` Retry Table — verify each row has a test:

| Retry type | maxRetries | Backoff | Test name pattern |
|-----------|-----------|---------|------------------|
| Sync API timeout | 3 | 5s fixed | `{flow}-sync-timeout-retry-test` |
| Async MQ | 3 | exp 30/90/270s | `{flow}-mq-retry-to-dlq-test` |
| Batch record | 1 | none | `{flow}-batch-record-retry-test` |
| Auth token expiry | 1 refresh | none | `{flow}-auth-refresh-test` |
| Notification | 2–3 | fixed 2–5s | `{flow}-notification-retry-test` |

## §13 — Logging Tests

Logging is verified by capturing logger output in MUnit and asserting log line structure.

### 13.1 Log Structure Rules (from standards)

Every log line must contain:
```
correlationId | flowName | timestamp | payloadSize | environment
```

Every log line must NOT contain:
```
credentials | PII (email, SSN, card) | raw payload bodies | full stack traces (in prod)
```

### 13.2 MUnit Logging Test Cases

| Test | What to assert | How |
|------|---------------|-----|
| **Correlation ID in every log** | Logger message contains correlationId value | Capture via `munit-tools:verify-call` on logger processor |
| **No PII in error log** | Error log line does not contain email/SSN pattern | Regex assertion on logger message capture |
| **No raw payload in WARN/ERROR log** | Log level WARN/ERROR lines do not echo full payload | Assert log message length < 500 chars (or specific field check) |
| **Log level per environment** | DEV logs DEBUG; PROD logs WARN+ | Property file token check; MUnit sets env var, assert logger level |
| **Connectivity error logged at ERROR** | HTTP:CONNECTIVITY triggers ERROR log | Assert logger level = ERROR via mock capture |
| **Validation error logged at WARN** | VALIDATION:NULL triggers WARN log | Assert logger level = WARN |
| **Notification failure logged at WARN** | Slack connector throws → WARN logged, not ERROR | Assert logger level = WARN |
| **Successful flow logs INFO (not DEBUG in uat/prod)** | Normal completion does not log DEBUG in prod | Assert log level ≠ DEBUG when `env=prod` property set |

### 13.3 Log Line Format Test

```xml
<!-- Test: verify log line format -->
<munit:test name="{flow}-log-format-test">
  <munit:behavior>
    <!-- Capture all logger calls -->
    <munit-tools:spy-event processor="logger" doc:name="Spy Logger"/>
  </munit:behavior>
  <munit:execution>
    <munit:run-flow name="{flow-name}">
      <munit:event>
        <munit:payload value='#[{ "id": "test-001" }]' mediaType="application/json"/>
        <munit:attributes value='#[{ headers: { "X-Correlation-ID": "log-test-correlation-001" }}]'/>
      </munit:event>
    </munit:run-flow>
  </munit:execution>
  <munit:validation>
    <!-- Assert correlationId appears in captured log messages -->
    <!-- Assert no PII field names (email, ssn, cardNumber) in any log message -->
    <!-- Assert flowName appears in log messages -->
  </munit:validation>
</munit:test>
```

## §19 — MUnit Coverage Report Interpretation

> Source: docs.mulesoft.com/munit/latest/coverage-maven-concept

MUnit generates three report artifacts after `mvn munit:test -Dmunit.coverage.runCoverage=true`:

| Report | Location | Use |
|--------|----------|-----|
| Surefire XML | `target/surefire-reports/TEST-*.xml` | CI/CD (GitHub Actions test reporter) |
| HTML report | `target/site/munit/coverage/` | Human review, customer evidence |
| JSON summary | `target/site/munit/coverage/munit-coverage.json` | Programmatic gate |

### What Coverage Measures

MUnit coverage counts executed **message processor** lines. It **excludes**:
- Connector operations (they are mocked — not real execution paths)
- Error handler lines (executed only on errors — counted separately)
- Logger operations

**Important:** A flow with only connector calls and a logger will show low coverage even with a complete happy-path test. Coverage is meaningful for flows that contain DataWeave transforms, choice routers, and validation logic — not for thin pass-through flows.

### Build Gate Configuration

```xml
<!-- In pom.xml (generated by scaffold) -->
<plugin>
    <groupId>com.mulesoft.munit.tools</groupId>
    <artifactId>munit-maven-plugin</artifactId>
    <configuration>
        <coverage>
            <runCoverage>true</runCoverage>
            <failBuild>true</failBuild>
            <requiredApplicationCoverage>{{MUNIT_COVERAGE}}</requiredApplicationCoverage>
            <requiredResourceCoverage>{{MUNIT_COVERAGE}}</requiredResourceCoverage>
            <requiredFlowCoverage>{{MUNIT_COVERAGE}}</requiredFlowCoverage>
            <formats>
                <format>console</format>
                <format>html</format>
                <format>sonar</format>
            </formats>
        </coverage>
    </configuration>
</plugin>
```
