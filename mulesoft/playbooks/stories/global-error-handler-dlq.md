# Story Template: Configure Global Error Handler and DLQ

**Story Type:** Global Infrastructure
**When to include:** Always — every project, generated once
**Priority:** P0 — must complete before any flow goes to dev
**Standard:** `standards/DESIGN_STANDARDS.md → Error Handling`
**Scenario files:** All patterns — applies universally
**Scaffold File:** `src/main/mule/error-handler.xml`

---

## User Story

As a developer, I need a global error handler that catches all unhandled exceptions, formats a standard error envelope, routes to DLQ after max retries, and never exposes stack traces, so that every integration flow has consistent failure behavior without per-flow error-handling code.

---

## Acceptance Criteria

### Error Handler Structure
- [ ] `error-handler.xml` exists at `src/main/mule/error-handler.xml`
- [ ] Global error handler declared and named `global-error-handler`
- [ ] Global error handler catches `ANY` exception type as the final catch-all
- [ ] `global-error-handler` is referenced in all `{domain}-flows.xml` files — NOT re-declared per flow
- [ ] No per-flow `<error-handler>` blocks unless the flow has documented reason to deviate (rare; requires tech lead sign-off)

### Error Envelope
- [ ] Every error path emits a standard envelope in this exact shape:
  ```json
  {
    "correlationId": "<string>",
    "errorCode": "<string>",
    "message": "<string>",
    "timestamp": "<ISO-8601>",
    "failingComponent": "<flow-name>"
  }
  ```
- [ ] No Java stack trace appears in any error response or log line at WARN or above
- [ ] `correlationId` is always present in the envelope — never null

### Retry and DLQ Routing
- [ ] Async MQ consumer retry strategy: 3 retries, exponential backoff 30s / 90s / 270s → publish to `{dlq-name}` after exhaustion
- [ ] Sync API retry strategy: 3 retries, 5s fixed → return HTTP 503 + `Retry-After` header
- [ ] MANUAL acknowledgement mode on all MQ consumers — `ACK` only after successful processing
- [ ] After max retries, message published to DLQ with original payload + error metadata
- [ ] DLQ queue name: `{queue-name}-dlq` (suffix, never a separate naming convention)
- [ ] Retry queue name (if used): `{queue-name}-retry`

### Notification Failures
- [ ] Slack/email/SMS notification calls wrapped in `on-error-continue` — NEVER break primary flow
- [ ] Notification retry: 2-3 attempts, fixed 2-5s delay, log WARN on final failure, continue always
- [ ] Notification failures are write-off by design — not retried to DLQ

### Validation Routing
- [ ] Validation failures (missing required field, wrong schema, unknown enum value) route to `{domain}-invalid-messages-queue` BEFORE any downstream connector call
- [ ] Validation errors are NOT routed to DLQ — they will always fail on retry and consume retry budget
- [ ] `on-error-continue` used for validation exceptions → route to invalid-message-channel

### MUnit Test
- [ ] MUnit test in `src/test/munit/error-handler-test.xml`
- [ ] Test: verify error envelope emitted with correct schema on simulated `MULE:ANY` exception
- [ ] Test: verify stack trace does not appear in error response body or log output
